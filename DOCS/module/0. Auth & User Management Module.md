# 0. Auth & User Management Module

**Module Type:** Platform Foundation  
**Build Phase:** Phase 1  
**Dependencies:** None (root module — every other module reads `user_id` from this module's identity)

---

## Purpose

Core identity, authentication, and session management. All multi-user isolation (RLS, `user_id` FKs, audit columns) depends on a trustworthy identity layer. The module is self-contained and portable: email + password (Argon2/bcrypt hashed), session tokens (hashed at rest), plus Google OAuth and magic-link flows, profile management, and GDPR-compliant account deletion.

## Functional Requirements

### Registration

**FR-A.1:** User signs up with email + password:
- Email is validated (format) and normalized (lowercased, trimmed)
- Password policy: min 8 chars, must contain letter + digit (configurable); the hash (Argon2id or bcrypt cost-10+) is stored in `users.hashed_password`
- Email uniqueness is enforced by the `UNIQUE (email)` constraint — a friendly "already registered" error is returned on conflict
- On success a `user_profiles` row, a `user_settings` row, and an initial `auth_tokens` session are created in the same transaction
- An email-verification token (`token_type = 'email_verify'`) is issued (optional until email delivery is configured; see F5 note)

**FR-A.2:** OAuth signup (Google): after the provider handshake, an existing email links to the existing account; a new email creates the account with `hashed_password` = NULL (OAuth-only login allowed). OAuth users can set a password later via F9 (requires provider-linked email verification).

**FR-A.3:** Magic-link signup/login (F4): a one-time token (`token_type = 'magic_link'`, 15-minute expiry) is emailed; consuming it logs the user in and, if the email was previously unregistered, creates the account in the same transaction.

### Login & Sessions

**FR-A.4:** Login verifies `hashed_password` against the input (constant-time compare). Success creates a session token; failure records a `login_attempts` row (for rate-limit/abuse detection) and an `access_logs` row with action `failed_login`.

**FR-A.5:** Session tokens are random 32-byte values; only the SHA-256 hash is stored in `auth_tokens.token_hash` (portable — see `data-tables-v2.md` § auth_tokens). The plain token is returned to the client once (Authorization header / httpOnly cookie).

**FR-A.6:** "Remember me" sets a longer session (30 days vs 24h default); otherwise sessions expire at `expires_at`. Expired sessions are rejected; `revoked_at` marks logout/revocation.

**FR-A.7:** Sessions rotate on login: a new token is issued and the previous one is revoked (unless "keep me signed in on this device" multi-session mode is enabled).

**FR-A.8:** User can view active sessions (device label, last seen, created) and revoke any of them from Settings → Security.

### Forgot Password & Password Change

**FR-A.9:** Forgot password issues a one-time reset token (`token_type = 'password_reset'`, 30-minute expiry, single-use via `revoked_at`) emailed as a reset link. Consuming it requires the new password to meet the policy (FR-A.1). Password reset invalidates all existing sessions. **Password reset does not affect the Secure Notes vault** — the vault key is re-wrapped with the new password via the recovery path (cross-ref Module 11 FR-11.14/FR-11.17).

**FR-A.10:** Password change (logged-in) requires the current password, updates the hash, revokes all other sessions, and records an `audit_logs` entry (action = UPDATE on `users`).

### Logout

**FR-A.11:** Logout marks the current token revoked (`revoked_at`) and clears client-side credentials. `access_logs` records action `logout`.

### Profile & Settings

**FR-A.12:** User profile fields: full name, email (changeable with re-verification), avatar (uploaded file → `avatar_url`). Stored in `user_profiles` (one row per user).

**FR-A.13:** User settings (currency, theme, language, notifications master switch, AI key/toggle) live in `user_settings` (one row per user) — see `data-tables-v2.md` § user_settings. Created at signup (FR-A.1); updated via Settings screens.

### Account Deletion (GDPR)

**FR-A.14:** Account deletion is a two-step flow (per Component C3 FR-C3.9): soft-delete marker immediately, permanent purge after a 30-day grace window, with a final data copy link emailed before purge. All user-owned rows cascade via FK `ON DELETE CASCADE`.

### Security

**FR-A.15:** Rate limiting on login/signup/password-reset endpoints (e.g., 5 attempts / 15 min / IP + email); `login_attempts` records every attempt with IP and user agent.

**FR-A.16:** Session timeout for inactive users (idle > 30 min → re-auth prompt; configurable in settings).

**FR-A.17:** All auth API endpoints run over HTTPS only; passwords are never logged, never stored plaintext, and never sent in query strings.

**FR-A.18 (Vault key lifecycle):** This module owns the vault-key lifecycle shared with Module 11 (Secure Notes):
- **Key derivation on login:** the client derives the vault wrap key (PBKDF2 from the password) and unwraps the stored vault key in the browser; the server is never handed the keys.
- **Key destruction on logout:** vault key + wrap key are zeroed in the client on logout and on idle session timeout (FR-A.16).
- **Password-reset impact:** resetting the password re-wraps the vault key with the new password via the recovery copy (`user_settings.vault_recovery_wrapped`, unwrapped server-side with the data-encryption key and delivered to the authenticated client). Vault data remains intact (Module 11 FR-11.14/FR-11.17).

**Session approach (portable):** tokens are hashed at rest, never stored plain. JWT can be layered in front without schema changes. One-time tokens (magic link, reset, verify) reuse the same table with `token_type` + single-use semantics (`revoked_at` stamped on consumption).

## Database Indexing Strategy

### Index Creation SQL

```sql
-- Unique constraints already enforce email / token lookups (O(log n)):
-- UNIQUE (email) on users, UNIQUE (token_hash) on auth_tokens
CREATE INDEX idx_auth_tokens_user ON auth_tokens(user_id, token_type, created_at DESC);
CREATE INDEX idx_access_logs_user ON access_logs(user_id, timestamp DESC);
CREATE INDEX idx_login_attempts_user ON login_attempts(user_id, timestamp DESC);
```

### Query Performance Benchmarks (Target)

| Query | Target Time | Index Used |
|-------|-------------|------------|
| Lookup user by email (login) | < 1ms | UNIQUE (email) |
| Lookup user by token hash | < 1ms | UNIQUE (token_hash) |
| Insert session token | < 2ms | PRIMARY KEY |
| Revoke token on logout | < 2ms | PRIMARY KEY |
| Get active sessions for a user | < 1ms | idx_auth_tokens_user |
| Record login attempt | < 2ms | PRIMARY KEY |

## Suggested Enhancements

1. **TOTP 2FA** — Add `totp_secret_encrypted` + `totp_enabled` to `users` and a 2FA challenge step at login.
2. **Device fingerprinting** — Store a device fingerprint on `auth_tokens` so the session list can show friendly device labels and flag unrecognized devices.
3. **Email verification enforcement** — Once transactional email is wired, block feature access until `email_verified_at` is set (with a resend-verification flow).
4. **WebAuthn / passkeys** — Passwordless device-bound auth as an alternative to magic links.
5. **Export personal data (GDPR)** — "Download my data" endpoint reusing Component C3's full-export pipeline.
6. **Password strength meter** — Client-side zxcvbn-style strength indicator on signup and password change forms.
