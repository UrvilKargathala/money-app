# 2. Transaction Engine Module

**Module Type:** Core Data Engine  
**Build Phase:** Phase 1  
**Dependencies:** Module 1 (Account & Wallet)

---

## Purpose

The Transaction Engine is the core data ingestion layer of MoneyMind. It handles all transaction entry (manual, CSV import, quick-add), categorization, search, filtering, duplicate detection, and pattern detection. Every other module (budgets, bills, goals, debt, tax, investments) reads from this module's data.

## Functional Requirements

### Manual Transaction Entry

**FR-2.1:** User can add a transaction with the following fields:
- Amount (required, positive decimal)
- Type (required, enum: income / expense / transfer)
- Account (required, selects from active accounts)
- Date (required, defaults to today's date)
- Description (required, free text or merchant name)
- Category (optional, auto-suggested based on description)
- Notes (optional, free text)
- Tags (optional, multi-select from existing tags)

**FR-2.2:** On save, account balances are recomputed from `opening_balance + SUM(signed transactions)`. No balance column is stored on the account — the account's displayed balance is derived on read:
- Income → increases balance
- Expense → decreases balance
- Transfer (from) → decreases source balance + creates paired credit on destination account
- Transfer (to) → increases destination balance

**FR-2.3:** Transaction insert is atomic within a single database transaction. If validation fails, the whole insert is rolled back. Balance math is deterministic (computed, not incrementally mutated), so no separate balance write is needed.

### Quick-Add Mode

**FR-2.4:** Quick-add mode shows a simplified input: amount field only + a "Save" button. The last-used merchant, category, account, and type are auto-populated from the most recent transaction.

**FR-2.5:** Quick-add displays a list of the 5 most recently used merchants as one-tap buttons. Tapping one pre-fills merchant name and category.

### CSV Import

**FR-2.6:** User can upload a CSV file. The app attempts auto-detection of column layout. If detection fails, a column mapping UI is shown.

**FR-2.7:** Column mapping UI displays the first 5 rows of the CSV with dropdown selectors for each column to map to transaction fields (Date, Description, Amount, Type, etc.). User confirmation is required before import.

**FR-2.8:** During import, each row is validated:
- Amount must be a valid number
- Date must be parseable (supports DD/MM/YYYY, MM/DD/YYYY, YYYY-MM-DD, DD-MMM-YYYY)
- Account must exist (default account is used if not specified)

**FR-2.9:** Invalid rows are collected in an error log with the specific reason. Valid rows are imported. User can download the error log as CSV for fixing.

**FR-2.10:** Import progress is displayed with a progress bar showing rows processed / total rows.

**FR-2.11:** Import summary is shown after completion: total rows, imported count, skipped count (duplicates), error count.

### Duplicate Detection

**FR-2.12:** On CSV import, each row is checked against existing transactions for potential duplicates. Match criteria: same amount + same description (fuzzy, 80% similarity) + same date ± 3 days.

**FR-2.13:** Suspected duplicates are shown in a review interface. User can: skip the duplicate (don't import), import anyway, merge with an existing transaction (combine the amounts and keep the earlier date; the duplicate is discarded), or apply the same action to all similar duplicates.

### Transaction List & Search

**FR-2.14:** Transaction list view displays: date, description, category (with color dot), account, amount (colored green for income, red for expense), tags, and action buttons (edit, delete).

**FR-2.15:** Default sort is by date descending (newest first). Sortable columns: date, amount, category, merchant (click a column header to change sort; direction toggles).

**FR-2.16:** Filters available:
- Date range (from / to)
- Account (dropdown, multi-select)
- Category (dropdown, multi-select)
- Type (income / expense / transfer)
- Amount range (min / max)
- Search text (fuzzy match on description)
- Tags (multi-select)

**FR-2.17:** Pagination with configurable page size (25, 50, 100 per page).

**FR-2.18:** Active filters are shown as removable chips/badges above the list.

### Transaction Edit & Delete

**FR-2.19:** Editing a transaction is a single atomic write. Displayed account balance is recomputed from `opening_balance + SUM(transactions)` (there is no stored balance to reverse).

**FR-2.20:** Deleting a transaction removes its row; the account's displayed balance is derived from the remaining transactions (computed, nothing to reverse explicitly).

**FR-2.21:** A confirmation dialog is shown before deletion: "Delete this transaction? This will update the account balance."

### Recurring Transactions

**FR-2.22:** User can create recurring transaction templates with pattern: frequency (daily / weekly / monthly / yearly), interval (every 1, 2, 3...), end condition (never / after N occurrences / on date).

**FR-2.23:** When a recurring transaction is due, a notification prompts the user to confirm and create the actual transaction.

### Import Tracking

**FR-2.24:** Every CSV import creates an import_batch record storing: filename, date range, total rows, imported rows, duplicate rows, error rows, status (completed / partial / failed).

**FR-2.25:** Import errors are persisted with row number, raw data, and error reason for debugging.

### Shared Expense Groups

**FR-2.26:** User can create a shared expense group with a name (required) and description (optional). The creator becomes the group **owner (admin)** — an `admin` row in `group_members` is created automatically. Every user is admin of the groups they create.

**FR-2.27:** Owner can invite members by email. Each invite generates a tokenized link with a 7-day expiry. Owner can revoke pending invites. Inviting a user who is already an active member is rejected.

**FR-2.28:** If the invitee has no MoneyMind account, the link routes to signup; on first login the group membership is auto-activated (read-only). If the invitee already has an account, the link shows a one-click accept page. Accepted invites consume the newest pending invite for that email and revoke older ones.

**FR-2.29:** The owner can attach any of their own transactions to a group at create/edit time (group selector on the transaction form, owner only). Detaching a transaction from a group does not delete it. Transactions remain owned by the owner's `user_id` — they continue to appear in the owner's personal dashboards, budgets, and reports.

**FR-2.30:** Read-only members see a group view listing the group's transactions (date, description, category, amount) with **no add / edit / delete actions**. Write access is enforced at the database level (no group-scoped INSERT/UPDATE/DELETE RLS policy) — hiding buttons is not the only defense.

**FR-2.31:** Owner can remove a member; members can leave a group. Leaving or removal never touches the owner's transactions; membership status flips to `removed` and read access to the group's transactions stops.

**FR-2.32:** Owner can transfer ownership to an active member: the new owner becomes `admin`, the old owner becomes a `read_only` member (unless they leave). Group transactions and the group itself remain intact.

> **Invite acceptance implementation note:** acceptance runs through a `SECURITY DEFINER` app function — validate the hashed token, expiry, and `pending` status → insert `group_members` (`role = 'read_only'`, `status = 'active'`) → mark the invite `accepted` and revoke older pending invites for the same email, all in one transaction (outside RLS by design). See `data-tables-v2.md` (RLS — Policy form E).

### Split Transactions

**FR-2.33:** User can split a transaction into 2+ category allocations (e.g., ₹1,000 at a grocery store → ₹700 Groceries + ₹300 Household). Splits are stored in `transaction_splits`; the parent transaction keeps its full amount and account linkage.

**FR-2.34:** The sum of all splits **must equal** the parent transaction's amount. The check is validated inside the same write transaction that inserts/updates/deletes splits — a violation rolls the whole write back. (Invariant enforced at the app layer; see `data-tables-v2.md` § transaction_splits.)

**FR-2.35:** Splits do not change account balance math (the parent amount already applies to the account). Splits exist so that budgets, reports, and category analytics aggregate spend per category through the splits.

**FR-2.36:** User can edit, delete, or add splits on an existing transaction. Removing the last split reverts the transaction to its original single category.

### Date-Grouped List & Daily Totals

**FR-2.37:** The transaction list can be grouped by date (default view). Each date group header shows the date and the day's total income / total expense (e.g., "Aug 5, 2026 · −₹1,240"). Group headers are sticky while scrolling.

**FR-2.38:** Ungrouped ("Flat list") view remains available via a toggle. Pagination applies per group in grouped mode.

### Expandable Row Detail

**FR-2.39:** Each row is expandable inline (no navigation). Expanded view shows: tags (with colors), notes, category path (parent → sub-category), merchant clean name, source (manual / CSV / quick-add), linked transfer group, split breakdown (if split), and inline actions: edit, delete, split.

**FR-2.40:** Expanding a row does not require a server round-trip — all row data is loaded with the list page (page-size row payload).

**Composite Indexes:**
```sql
-- Primary query pattern: get transactions for a user+account within a date range
CREATE INDEX idx_txn_account_date ON transactions(user_id, account_id, date);
-- Primary query pattern: get transactions by category within a date range
CREATE INDEX idx_txn_category_date ON transactions(user_id, category_id, date);
```
> No `COLLATE NOCASE` (SQLite-only). Fuzzy text search uses PostgreSQL `ILIKE` / `pg_trgm` (see `idx_txn_description_trgm` / `idx_txn_merchant_trgm`), not a NOCASE index.

**Performance Notes:**
- This will be the largest table in the app. Heavy usage: ~5-10 transactions/day = ~1,800-3,650/year = ~36,000-73,000 over 20 years per user
- All queries filter by `user_id` first (multi-user isolation), then `account_id` or `date`, all indexed
- The composite indexes `(user_id, account_id, date)` and `(user_id, category_id, date)` serve 90% of all queries as covering indexes
- Balance is **computed** on read (`opening_balance + SUM(amount)`), not stored on the account — no write amplification on every transaction

**Tree rules (canonical, enforced at app level):**
- The tree is **exactly 2 levels deep**: system parents (seeded) + leaf sub-categories. Users may create custom categories at either level, but not deeper than 2 levels.
- **Transactions always resolve to a leaf category** (`transactions.category_id`). A parent category is never assigned directly to a transaction — parent totals are aggregates over their leaf descendants.
- Budgets (Module 3) may target a leaf or a parent category. A parent budget's actual spend = `SUM` of transactions on its leaf sub-categories (see FR-3.23/3.24 for the breakdown rule).
- Custom user categories (`user_id IS NOT NULL`) follow the same rules; they are scoped per user (`ux_categories_user_name`) and never override system names (`ux_categories_system_name`).

### Table: group_invites

Email invites with self-signup support (FR-2.27 / FR-2.28). Token hashed at rest (same rule as `auth_tokens`); the plain token travels in the link.

| Column | Type | Constraints | Index | Description |

| invited_by | INTEGER | FK → users(user_id) | | Inviter |
| expires_at | TIMESTAMPTZ | NOT NULL | | Default 7 days |

## Database Indexing Strategy

### Index Creation SQL

```sql
-- Transactions table (multi-user aware)
CREATE EXTENSION IF NOT EXISTS pg_trgm;  -- core PostgreSQL contrib; enables ILIKE '%...%' fuzzy search
CREATE INDEX idx_txn_account_date ON transactions(user_id, account_id, date);
CREATE INDEX idx_txn_category_date ON transactions(user_id, category_id, date);
CREATE INDEX idx_txn_transfer ON transactions(transfer_group_id);
-- Group-scoped view: active members read group transactions (FR-2.30)
CREATE INDEX idx_txn_group ON transactions(group_id, date DESC);
-- Fuzzy text search on description / merchant name (FR-2.16)
CREATE INDEX idx_txn_description_trgm ON transactions USING GIN (description gin_trgm_ops);
CREATE INDEX idx_txn_merchant_trgm ON transactions USING GIN (merchant_clean gin_trgm_ops);

-- Categories
CREATE UNIQUE INDEX ux_categories_system_name ON categories(name) WHERE user_id IS NULL;
CREATE UNIQUE INDEX ux_categories_user_name ON categories(user_id, name) WHERE user_id IS NOT NULL;
CREATE INDEX idx_cat_parent ON categories(parent_id);

-- Merchant Mappings
CREATE UNIQUE INDEX idx_mm_merchant ON merchant_mappings(user_id, merchant_raw);

-- Tags
CREATE UNIQUE INDEX idx_tag_name ON tags(user_id, name);

-- Transaction-Tags join
CREATE UNIQUE INDEX idx_tt_pair ON tags_transactions(user_id, transaction_id, tag_id);
CREATE INDEX idx_tt_tag ON tags_transactions(tag_id);

-- Transaction Splits (F16)
CREATE UNIQUE INDEX idx_ts_pair ON transaction_splits(user_id, transaction_id, category_id);
CREATE INDEX idx_ts_category ON transaction_splits(user_id, category_id);

-- Recurring Transaction Templates
CREATE INDEX idx_recrt_active ON recurring_transaction_templates(is_active);
CREATE INDEX idx_recrt_next ON recurring_transaction_templates(next_due_date);

-- Import tracking
CREATE INDEX idx_ib_status ON import_batches(status);
CREATE INDEX idx_ie_batch ON import_errors(import_batch_id);

-- Shared Expense Groups (F15)
CREATE UNIQUE INDEX ux_gm_pair ON group_members(group_id, user_id);
CREATE UNIQUE INDEX ux_gm_active_user ON group_members(user_id, group_id) WHERE status = 'active';
CREATE UNIQUE INDEX ux_gi_token ON group_invites(token_hash);
```

## Suggested Enhancements

1. **Bulk edit mode** — A mode where users can select multiple transactions (checkboxes) and apply a bulk action: change category, add/remove tags, delete. Essential for fixing imports where multiple transactions got the wrong category.

2. **Transaction templates** — Allow users to save common transactions as templates (e.g., "Monthly Rent — ₹15,000 — HDFC Savings — Housing"). Selecting a template pre-fills all fields. Different from recurring transactions (which auto-create).

3. **Split transactions** — One transaction that maps to multiple categories. Example: A ₹1,000 grocery store purchase where ₹700 is Groceries and ₹300 is Household Supplies. Requires a `transaction_splits` table.

4. **Receipt attachment** — Allow users to attach an image of the receipt/bill to a transaction. Useful for returns, warranty claims, and tax documentation. Store the file path (not the file itself) in the transactions table.

5. **Undo/redo** — Maintain an in-memory action stack for the last 10 transaction operations (create, edit, delete). User can press Ctrl+Z to undo. Since balance recalculation is involved, this provides a safety net.

6. **Running balance column** — When viewing transactions for a single account, show the running balance after each transaction (like a bank statement). This is a display-time calculation using a window function, not a stored column.

7. **Memo/check number field** — Some users track cheque numbers. Adding an optional `reference_number` field to transactions would cover this without needing a dedicated cheque module.

8. **Scheduled balance audit** — A periodic background check that recalculates every account balance from opening_balance + all transactions and alerts if any discrepancy is found. Catches bugs or manual DB edits.
