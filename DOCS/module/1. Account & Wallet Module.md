# 1. Account & Wallet Module

**Module Type:** Foundation  
**Build Phase:** Phase 1  
**Dependencies:** None (this is a root module)

---

## Purpose

The Account & Wallet Layer is the foundation of MoneyMind. Every transaction, bill, debt payment, goal contribution, and investment references an account. This module manages the creation, tracking, health monitoring, and balance history of all financial accounts the user owns.

## Functional Requirements

### Account CRUD

**FR-1.1:** User can create an account with the following fields:
- Name (required, e.g., "HDFC Savings")
- Type (required, enum: bank_savings, bank_current, credit_card, wallet, cash, fd, ppf)
- Institution (optional, e.g., "HDFC Bank")
- Opening Balance (decimal, defaults to 0)
- Credit Limit (only for credit_card type, optional)
- Currency (defaults to INR)
- Color (for UI display, auto-assigned if not chosen)
- Notes (optional text)

**FR-1.2:** Account balance reflects every linked transaction (computed on read from `opening_balance + SUM(signed transactions)`; no stored balance column):
- Income transaction → balance increases
- Expense transaction → balance decreases
- Transfer (from this account) → balance decreases
- Transfer (to this account) → balance increases

**FR-1.3:** Balance math is deterministic — since it is derived from transactions, editing or deleting a transaction automatically changes the displayed balance with no separate recalculation step.

**FR-1.4:** User can view all accounts in a single dashboard sorted by type then by balance (descending), showing:
- Account name, institution, type (with icon), current balance
- Credit utilization % for credit cards
- Total aggregate balance across all accounts
- Total assets (savings + current + wallet + cash + fd + ppf balances)
- Total liabilities (credit card balances)
- Net balance (assets - liabilities)

**FR-1.5:** User can edit account name, institution, notes, color, and credit limit. Opening balance cannot be edited after creation (user must create a balance correction transaction instead).

**FR-1.6:** User can deactivate (soft-delete) an account. Deactivated accounts:
- Are hidden from the main dashboard by default
- Can be viewed via a "Show deactivated accounts" toggle
- Cannot have new transactions linked to them
- Retain all historical transaction data

**FR-1.7:** User can permanently delete an account only if it has zero transactions and zero balance. Otherwise, deactivation is enforced.

**FR-1.8:** Account creation date is recorded and displayed. Account age is shown in months/years.

### Balance History

**FR-1.9:** A daily balance snapshot is recorded for each account at the end of each day (or on first launch of a new day). This enables the balance history chart without scanning all transactions.

**FR-1.10:** Balance history is viewable as a line chart with date range selector (1M, 3M, 6M, 1Y, 5Y, All, Custom Range).

**FR-1.11:** Hovering over any point on the chart shows: date, balance, net change from previous day.

### Credit Card Specific

**FR-1.12:** For credit_card accounts, the UI displays:
- Current balance (amount owed)
- Credit limit
- Utilization percentage: (balance / credit_limit) * 100
- Available credit: credit_limit - balance
- Color-coded utilization indicator: green (< 30%), yellow (30-50%), orange (50-80%), red (> 80%)

**FR-1.13:** User can update the credit limit on a credit card account at any time (limits can change).

### Account Transfers (Own Accounts)

**FR-1.14:** User can transfer money between their own accounts. A single transfer creates two transaction records:
- One debit transaction on the source account
- One credit transaction on the destination account
- Both share the same `transfer_group_id` for linking

> **Atomicity (E3):** The two transaction rows (debit + credit) **plus** the `account_transfers` row are created in a single database transaction. If any one fails, the entire transfer rolls back — no orphaned debit/credit pairs.

**FR-1.15:** Transfer history is viewable in a dedicated "Transfers" tab showing: date, from account, to account, amount, and any notes.

### Data Export

**FR-1.16:** User can export the account list as CSV with columns: Name, Type, Institution, Balance, Credit Limit (if applicable), Created Date, Status (active/deactivated).

**FR-1.17:** User can export the balance history chart as PDF/PNG for any selected date range.

### Account List Filters

**FR-1.18:** The account dashboard has a type filter dropdown (All / bank_savings / bank_current / credit_card / wallet / cash / fd / ppf) plus the "Show deactivated accounts" toggle (from FR-1.6) in the same filter bar. Filtering is applied client-side on the loaded list — no search box is needed at 10–50 accounts per user. The account picker dropdown keeps its lightweight name typeahead, also client-side.

## Data Tables

### Table: accounts

The primary table storing all account information. **Balance is computed, not stored** — balance = `opening_balance + SUM(signed transactions)` (indexed range scan). See canonical schema in `../data-tables-v2.md` § Module 1.

| Column | Type | Constraints | Index | Description |
|--------|------|-------------|-------|-------------|
| id | UUID | PK, DEFAULT gen_random_uuid() | PRIMARY KEY | UUID |
| user_id | INTEGER | NOT NULL, FK → users(user_id) ON DELETE CASCADE | INDEX idx_accounts_user_id | Multi-user owner |
| name | TEXT | NOT NULL | | Display name (e.g., "HDFC Savings") |
| type | TEXT | NOT NULL, CHECK(type IN ('bank_savings','bank_current','credit_card','wallet','cash','fd','ppf')) | | Account category |
| institution | TEXT | | | Bank or institution name |
| opening_balance | NUMERIC(12,2) | NOT NULL DEFAULT 0 | | Initial balance at creation |
| credit_limit | NUMERIC(12,2) | | | Only for credit_card type |
| currency | TEXT | NOT NULL DEFAULT 'INR' | | ISO currency code |
| color | TEXT | | | Hex color for UI |
| notes | TEXT | | | User notes |
| is_active | INTEGER | NOT NULL DEFAULT 1 | | 1 = active, 0 = deactivated |
| sort_order | INTEGER | NOT NULL DEFAULT 0 | | Display order |
| version | INTEGER | NOT NULL DEFAULT 1 | | Optimistic lock |
| created_by | INTEGER | FK → users(user_id) | | Audit |
| updated_by | INTEGER | FK → users(user_id) | | Audit |
| deleted_at | TIMESTAMPTZ | | | Soft delete (deactivate) |
| deleted_by | INTEGER | FK → users(user_id) ON DELETE SET NULL | | Who deactivated |
| created_at | TIMESTAMPTZ | NOT NULL DEFAULT CURRENT_TIMESTAMP | | Created timestamp |
| updated_at | TIMESTAMPTZ | NOT NULL DEFAULT CURRENT_TIMESTAMP | | App-managed timestamp |

**Performance Notes:**
- PRIMARY KEY on `id` gives fast single-account lookups (O(log n), ~0.1ms for 100 accounts)
- `idx_accounts_user_id` binds every query to the owning user (multi-user enforcement)
- Search-by-name in the account picker is a client-side typeahead over the loaded list (10–50 rows/user; no index needed)
- Money is `NUMERIC(12,2)` — never `REAL`/floating point. Balance is computed on read from `opening_balance` + signed transactions (see canonical schema).

**Estimated row count:** 10-50 accounts per user lifetime. Even with 100 accounts, every query is sub-millisecond.

### Table: account_balance_history

Daily snapshots of account balances for charting and trend analysis (safe denormalization).

| Column | Type | Constraints | Index | Description |
|--------|------|-------------|-------|-------------|
| id | UUID | PK, DEFAULT gen_random_uuid() | PRIMARY KEY | UUID |
| user_id | INTEGER | NOT NULL, FK → users(user_id) ON DELETE CASCADE | | Multi-user owner (covered by composite `idx_abh_account_date`) |
| account_id | UUID | NOT NULL, FK → accounts(id) ON DELETE CASCADE | | Account reference (covered by composite) |
| balance | NUMERIC(12,2) | NOT NULL | | Balance at the end of the day |
| date | DATE | NOT NULL | | Business date (covered by composite) |

**Composite Index:**
```sql
CREATE UNIQUE INDEX idx_abh_account_date ON account_balance_history(user_id, account_id, date);
```
This ensures:
- One snapshot per account per day (no duplicates)
- Fast lookup: "get all balance snapshots for account X between dates Y and Z" — the most common query pattern
- Multi-user isolation (scoping by `user_id`)
- Sorting by (account_id, date) is free (index is already sorted)

**Performance Notes:**
- Daily snapshots for 10 accounts over 20 years = 10 × 365 × 20 = **~73,000 rows**
- The composite index query `WHERE user_id = ? AND account_id = ? AND date BETWEEN ? AND ?` runs in ~0.2ms
- Chart rendering queries for 5 years of data (~1,825 rows) complete in under 2ms

### Table: account_transfers

Links transfer transactions between the user's own accounts.

| Column | Type | Constraints | Index | Description |
|--------|------|-------------|-------|-------------|
| id | UUID | PK, DEFAULT gen_random_uuid() | PRIMARY KEY | UUID |
| user_id | INTEGER | NOT NULL, FK → users(user_id) ON DELETE CASCADE | | Multi-user owner |
| transfer_group_id | UUID | NOT NULL | INDEX idx_at_group | Shared ID linking debit + credit transaction pair |
| from_account_id | UUID | NOT NULL, FK → accounts(id) | INDEX idx_at_from | Source account |
| to_account_id | UUID | NOT NULL, FK → accounts(id) | INDEX idx_at_to | Destination account |
| from_transaction_id | UUID | NOT NULL, FK → transactions(id) | | Debit transaction on source |
| to_transaction_id | UUID | NOT NULL, FK → transactions(id) | | Credit transaction on destination |
| amount | NUMERIC(12,2) | NOT NULL, CHECK > 0 | | Transfer amount |
| date | DATE | NOT NULL | INDEX idx_at_date | Transfer date |
| notes | TEXT | | | Optional user notes |
| version | INTEGER | NOT NULL DEFAULT 1 | | Optimistic lock |
| created_at | TIMESTAMPTZ | NOT NULL DEFAULT CURRENT_TIMESTAMP | | Created timestamp |

**Indexes:**
```sql
CREATE INDEX idx_at_from ON account_transfers(from_account_id);
CREATE INDEX idx_at_to ON account_transfers(to_account_id);
CREATE INDEX idx_at_date ON account_transfers(date);
```

**Performance Notes:**
- Each transfer generates exactly 2 transaction rows (one debit, one credit) linked by `transfer_group_id`
- The "Transfers" tab queries `WHERE user_id = ? AND (from_account_id = ? OR to_account_id = ?) ORDER BY date DESC` — both columns are indexed
- Estimated rows: 50-500 transfers per user per year. Even at 10,000 rows, queries complete in <1ms

## Database Indexing Strategy

### Index Creation SQL

```sql
-- Accounts table indexes (multi-user aware)
CREATE INDEX idx_accounts_user_id ON accounts(user_id);

-- Account Balance History indexes
CREATE UNIQUE INDEX idx_abh_account_date ON account_balance_history(user_id, account_id, date);

-- Account Transfers indexes
CREATE INDEX idx_at_from ON account_transfers(from_account_id);
CREATE INDEX idx_at_to ON account_transfers(to_account_id);
CREATE INDEX idx_at_date ON account_transfers(date);
CREATE INDEX idx_at_group ON account_transfers(transfer_group_id);
```

### Query Performance Benchmarks (Target)

| Query | Target Time | Index Used |
|-------|-------------|------------|
| Get account by ID (scoped to user) | < 1ms | PRIMARY KEY + idx_accounts_user_id |
| Get all active accounts for a user sorted by type | < 1ms | idx_accounts_user_id (filter active in app/seq) |
| Get balance history for account (1 year) | < 2ms | idx_abh_account_date |
| Get balance history for account (20 years) | < 3ms | idx_abh_account_date |
| Get all transfers involving account X | < 1ms | idx_at_from + idx_at_to |
| Insert new account | < 5ms | PRIMARY KEY |
| Insert daily balance snapshot | < 5ms | idx_abh_account_date (unique check) |
| Export all accounts as CSV (scoped to user) | < 10ms | idx_accounts_user_id |
| Compute balance on read (opening_balance + SUM txn) | < 2ms | idx_txn_account_date |

## Suggested Enhancements

1. **Reconciliation feature** — A future enhancement where the user can mark a month as "reconciled" after verifying the account balance matches their bank statement. Reconciliation locks past transactions from editing and provides a clear audit trail.

2. **Account icons** — Allow users to pick from a set of bank/institution logos or upload custom icons for each account. Makes the dashboard visually scannable.

3. **Balance correction transactions** — Instead of directly editing `opening_balance`, provide a "Balance Correction" transaction type that adjusts the balance with an audit trail. This prevents silent balance edits that could break transaction-to-balance reconciliation.

4. **Multi-currency support** — Store the `currency` field per account now (already in schema) and add a `conversion_rate_to_inr` field. Even if not used in Phase 1, having the column avoids a migration later. For Phase 1, default all accounts to INR.

5. **Minimum balance alerts** — Allow users to set a minimum balance threshold per account. If balance drops below, the system flags a notification.

6. **Account archive (vs deactivate)** — Deactivate means "no new transactions." Archive means "hide from view but still receive auto-updates." Currently we only have deactivate. Adding an `is_archived` boolean would give more flexibility.
