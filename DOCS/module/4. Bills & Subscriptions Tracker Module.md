# 4. Bills & Subscriptions Tracker Module

**Module Type:** Tracking & Reminder  
**Build Phase:** Phase 2  
**Dependencies:** Module 1 (Account & Wallet), Module 2 (Transaction Engine)

---

## Purpose

Tracks all recurring financial obligations — both fixed bills (rent, EMIs, utilities, insurance premiums) and subscriptions (streaming services, SaaS, gym memberships, app subscriptions). Provides a unified view of all recurring outflows, payment reminders, and payment history tracking.

## Functional Requirements

### Bill Management

**FR-4.1:** User can create a bill with:
- Name (required, e.g., "Rent", "Electricity Bill")
- Amount (required for fixed bills; optional for variable bills, estimated amount used)
- Due Day (required, day of month 1-31. If 31st doesn't exist in a month, use last day)
- Frequency (required, enum: monthly / quarterly / half_yearly / annual / one_time)
- Account (required, linked payment account)
- Category (optional, defaults to "Bills & Services")
- Notes (optional)
- Reminder (optional: 1 day before / 3 days before / 7 days before / custom)

**FR-4.2:** Variable bills (utilities, electricity, water) allow the amount to change each period. User enters the actual amount when marking it as paid. The estimated amount is used for the monthly obligation calculation.

**FR-4.3:** Bill calendar shows the next 30 days with bill due dates marked. Each bill shows: name, amount, and days until due. Overdue bills are highlighted in red.

**FR-4.4:** Marking a bill as paid:
- User clicks "Mark as Paid" on the bill
- If fixed amount: auto-filled. If variable: user enters the actual amount.
- Optionally select the linked account for payment (defaults to the bill's account)
- On confirm: a transaction is created in the Transaction Engine (expense type) with description: "Rent — July 2026" or similar
- The bill's status for that period updates to "paid"
- The payment is recorded in payment_history

**FR-4.5:** Bill payment statuses:
- **Upcoming** — due date hasn't arrived yet
- **Due Soon** — due within 3 days
- **Overdue** — past due date, not marked as paid
- **Paid** — marked as paid for the current period
- **Skipped** — user explicitly skipped this period (e.g., waived fee)

**FR-4.5a:** `current_period_status` is stored, but `due_soon` and `overdue` are time-dependent. A **daily background job** (node-cron worker, see `DOCS/DEV-ENV.md` § 10) recomputes time-based statuses for every active bill's current period (`upcoming` → `due_soon` → `overdue` based on `due_day` and today's date). `paid` and `skipped` are user-set and are never overwritten by the job.

**FR-4.6:** User can edit bill details. Changes apply to the next period forward. Past periods retain their original data.

**FR-4.7:** User can deactivate a bill. Deactivated bills are hidden from the main view but retain history. Can be reactivated.

### Subscription Management

**FR-4.8:** User can create a subscription with:
- Service Name (required, e.g., "Netflix Premium")
- Amount (required, positive decimal)
- Frequency (required, enum: monthly / quarterly / annual)
- Next Renewal Date (required)
- Category (optional, defaults to "Entertainment")
- Account (optional, if payment account is known)
- Notes (optional)

**FR-4.9:** Subscription list displays:
- Service name and icon/category color
- Amount per billing cycle and monthly equivalent
- Next renewal date with countdown
- Status (active / paused / cancelled)
- Total monthly burn: sum of all active subscription monthly-equivalent amounts

**FR-4.10:** User can pause a subscription. Paused subscriptions are shown in a separate section and don't count toward monthly burn.

**FR-4.11:** User can cancel a subscription. Cancelled subscriptions are archived with a "Cancelled on [date]" label. They retain history.

**FR-4.12:** When a subscription renewal date passes, the system shows it as "Due for Renewal" and prompts the user to either confirm renewal (creates a transaction) or snooze.

### List Filters

**FR-4.20:** The bills list has status filter tabs: All / Upcoming / Due Soon / Overdue / Paid / Skipped (mapped to `current_period_status`). Deactivated bills stay hidden by default (FR-4.7) with a "Show deactivated" toggle in the same filter bar. Filtering is applied client-side on the loaded list.

**FR-4.21:** The subscriptions list has status filter tabs: All / Active / Paused / Cancelled. The total monthly burn (FR-4.9) always reflects Active subscriptions only, regardless of the active tab. Filtering is applied client-side on the loaded list.

**FR-4.22:** Bills and subscriptions remain two tabbed lists with a combined-count summary header (total items, total monthly obligation). Note: if the combined list ever grows past ~30 items, revisit adding a search box (per search-and-filter-strategy.md) — status tabs alone are sufficient at current scale.

### Auto-Pay Indicator

**FR-4.23:** User can mark a bill as handled by auto-debit (`bills.is_autopay = 1`). Auto-pay bills:
- Show an "Auto-pay" badge on the bill card, the 30-day bill calendar, and the Financial Calendar (Component C1)
- Still generate payment reminders (the user may want to verify funds), but the badge signals no manual action is required
- Are counted normally in monthly obligation and cash flow projection (the debit still leaves the account)

### Cash Flow Impact Waterfall

**FR-4.24:** For any account, the user can view a balance waterfall chart covering the upcoming billing period: starting balance, then a step down per scheduled bill/subscription payment (in date order), with the projected ending balance labeled. Steps whose payment would drop the balance below ₹0 (or below the account's minimum-balance threshold, Module 1 enhancement) are highlighted in red.

**FR-4.25:** The waterfall reuses the Component C1 daily cash flow projection data (FR-C1.9) and Module 1 computed balances — no separate storage. This satisfies the feature-list requirement "Cash flow impact visualization (balance waterfall after upcoming bills)".

### Payment History

**FR-4.13:** Each bill and subscription has a payment history tab showing: payment date, amount, linked transaction ID, period (e.g., "July 2026"), and any notes.

**FR-4.14:** Payment history for bills shows year-over-year comparison: "Last year this month: ₹3,200 | This year: ₹3,500"

### Dashboard & Overview

**FR-4.15:** A dashboard widget shows:
- Total monthly obligation (sum of all active bills + subscriptions)
- Number of bills due this week
- Number of overdue items
- Monthly burn trend (this month vs last month)
- Upcoming calendar with next 5 due items

**FR-4.16:** User can view a monthly cash flow projection showing: upcoming bills, expected income (from recurring income transactions), and predicted remaining balance per account.

### Export

**FR-4.17:** Export bills list as CSV with columns: Name, Amount, Due Day, Frequency, Account, Status, Last Paid Date.

**FR-4.18:** Export subscriptions list as CSV with columns: Service Name, Amount, Frequency, Monthly Equivalent (computed on read), Next Renewal, Status.

**FR-4.19:** Export payment history for any bill/subscription as CSV.

## Data Tables

### Table: bills

Tracks all recurring bills with amounts, due dates, and payment status.

> `last_paid_date` / `last_paid_amount` were removed (duplicated in `payment_history`, drift risk) — derive the latest payment from `payment_history` on read. `is_variable` was removed — a bill is variable when `amount IS NULL`.

| user_id | INTEGER | NOT NULL, FK → users(user_id) ON DELETE CASCADE | | Multi-user owner (covered by composite `idx_bill_status_active`) |
| name | TEXT | NOT NULL | | Bill name (e.g., "Rent", "Electricity") |
| amount | NUMERIC(12,2) | | | Fixed amount (NULL = variable bill; detect via `amount IS NULL`) |

### Table: payment_history

Records every payment made against a bill or subscription.

| Column | Type | Constraints | Index | Description |
|--------|------|-------------|-------|-------------|
| id | UUID | PK, DEFAULT gen_random_uuid() | PRIMARY KEY | UUID |
| user_id | INTEGER | NOT NULL, FK → users(user_id) ON DELETE CASCADE | | Multi-user owner (covered by composite `idx_ph_payable_period`) |
| payable_type | TEXT | NOT NULL, CHECK(payable_type IN ('bill','subscription')) | | Type of payable |
| payable_id | UUID | NOT NULL | INDEX idx_ph_payable | References bills.id or subscriptions.id |
| transaction_id | UUID | FK → transactions(id) | INDEX idx_ph_transaction | Linked transaction (created on payment) |
| amount | NUMERIC(12,2) | NOT NULL, CHECK(amount > 0) | | Amount paid |
| period_label | TEXT | NOT NULL | | Period (e.g., "July 2026") |
| period_month | INTEGER | NOT NULL, CHECK(period_month BETWEEN 1 AND 12) | | Month of period |
| period_year | INTEGER | NOT NULL | | Year of period |
| notes | TEXT | | | Optional user notes |
| created_at | TIMESTAMPTZ | NOT NULL DEFAULT CURRENT_TIMESTAMP | INDEX idx_ph_created | Created timestamp |

**Composite Indexes:**
```sql
-- Primary query: payment history for a specific bill/subscription (per user)
CREATE INDEX idx_ph_payable_period ON payment_history(user_id, payable_id, payable_type, period_year, period_month);
-- Year-over-year comparison query
CREATE INDEX idx_ph_period ON payment_history(user_id, payable_type, payable_id, period_year);
```

> **Application-enforced FK:** `payable_id` is a polymorphic reference (`payable_type` decides whether it points at `bills.id` or `subscriptions.id`). PostgreSQL cannot enforce a foreign key on it — referential integrity is **enforced in the application layer**, which must also handle cascading deletes: deleting a bill/subscription deletes its `payment_history` rows in the same write transaction. Joins resolve the target via `CASE`/two-branch UNION.

**Performance Notes:**
- Monthly payments for 20 bills over 20 years = 20 × 12 × 20 = **~4,800 rows** per user
- Adding subscriptions, total is around 25 × 12 × 20 = **~6,000 rows** per user
- Composite index `idx_ph_payable_period` serves the "show payment history for this bill" query in < 1ms

## Database Indexing Strategy

### Index Creation SQL

```sql
-- Bills table (multi-user aware)
CREATE INDEX idx_bill_account ON bills(account_id);
CREATE INDEX idx_bill_status_active ON bills(user_id, current_period_status, is_active);
CREATE INDEX idx_bill_due_active ON bills(user_id, due_day, is_active);

-- Subscriptions table
CREATE INDEX idx_sub_account ON subscriptions(account_id);
CREATE INDEX idx_sub_active_renewal ON subscriptions(user_id, status, next_renewal_date);

-- Payment History
CREATE INDEX idx_ph_payable ON payment_history(payable_id, payable_type);
CREATE INDEX idx_ph_payable_period ON payment_history(user_id, payable_id, payable_type, period_year, period_month);
CREATE INDEX idx_ph_period ON payment_history(user_id, payable_type, payable_id, period_year);
CREATE INDEX idx_ph_transaction ON payment_history(transaction_id);
CREATE INDEX idx_ph_created ON payment_history(created_at);

-- Bill Reminders
CREATE INDEX idx_br_bill ON bill_reminders(bill_id);

-- Subscription Audits
CREATE INDEX idx_sal_sub ON subscription_audits(subscription_id);
CREATE INDEX idx_sal_type ON subscription_audits(audit_type);
CREATE INDEX idx_sal_created ON subscription_audits(created_at);
```

### Query Performance Benchmarks (Target)

| Query | Target Time | Index Used |
|-------|-------------|------------|
| Get all active bills sorted by due day (user) | < 0.5ms | idx_bill_due_active |
| Get all overdue bills (user) | < 0.5ms | idx_bill_status_active (filter overdue) |
| Get upcoming bills for next 30 days (user) | < 1ms | idx_bill_due_active |
| Get all active subscriptions (user) | < 0.5ms | idx_sub_active_renewal |
| Get total monthly burn (user, SUM of active subs) | < 0.5ms | idx_sub_active_renewal (aggregate) |
| Get payment history for a bill (user, all time) | < 1ms | idx_ph_payable_period |
| Get year-over-year comparison for a bill | < 1ms | idx_ph_period |
| Mark bill as paid (create transaction + update status) | < 2ms | PRIMARY KEY + idx_ph_payable |
| Get upcoming renewals for next 7 days (user) | < 2ms | idx_sub_active_renewal |
| Calculate total monthly obligation (bills + subs, user) | < 1ms | idx_bill_status_active + idx_sub_active_renewal |

## Suggested Enhancements

1. **Recurring pattern auto-detection (AI assist)** — In Phase 4, add a background scan of the last 90 days of transactions that identifies recurring debits and suggests them as bills or subscriptions. The user can one-click add them. This reduces manual setup friction significantly.

2. **Bill splitting** — For bills shared with roommates or family (rent, electricity, internet), allow the user to track their share vs total. The bill amount shows as "₹15,000 (Your share: ₹5,000)." This is useful even in a personal app if the user manages shared household expenses.

3. **Price hike detection** — Compare current subscription amounts to the first recorded payment. If a service has increased prices (e.g., Netflix went from ₹199 to ₹299), flag it automatically. Users often don't notice gradual price increases.

4. **Subscription usage tracking** — An optional field on subscriptions: "Last used date." User updates this when they use the service. If a subscription hasn't been used in 60+ days, flag it as potentially wasted money. This helps users decide what to cancel.

5. **Upcoming month snapshot** — A printable/saveable snapshot of the next month showing: all bills due with amounts, expected income, and predicted ending balance per account. Useful for the user to pin on their desk or keep as a reference.

6. **Bill payment scheduling** — Allow users to set a "pay on" date that is different from the due date. Some users pay bills early. The system tracks the scheduled payment date separately from the due date and sends the reminder on the scheduled date instead.
