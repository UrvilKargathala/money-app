# 11. Secure Notes & Vault Module

**Module Type:** Encrypted Storage  
**Build Phase:** Phase 2  
**Dependencies:** Auth & User Management (identity), App Shell (search, settings)

---

## Purpose

A password-manager-style vault for sensitive personal data: passwords, OTT plans, bank and card details, insurance policies, document IDs, WiFi credentials, and freeform notes. The module follows the Security requirement that **passwords and sensitive values are never sent as plaintext** — all sensitive content is encrypted client-side (AES-256-GCM) before any network write, with only ciphertext stored at rest. The server never sees the plaintext.

## Functional Requirements

### Note Creation & Management

**FR-11.1:** User can create a note with:
- Title (required)
- Category (required; defaults to "Personal"; pick from the seeded list or type a custom category)
- Content (freeform rich text for F11, or structured template fields for F4–F10)

**FR-11.2:** A note is either **template-based** (stores a JSON payload of the template's fields) or **freeform** (`template_code` = NULL). A note cannot be both.

**FR-11.3:** User can edit a note's title, category, and content at any time. Edits re-encrypt the payload and increment `version` (optimistic lock).

**FR-11.4:** User can delete a note (soft delete). Deleted notes are hidden from the list and can be restored within 30 days or permanently purged.

**FR-11.5:** User can pin/unpin a note. Pinned notes sort to the top of the list; the pinned order is stable within the pinned group.

### Categories

**FR-11.6:** The category picker shows the 10 seeded categories plus any custom categories the user has created. Categories are stored as free text on the note (`category` column) — no separate category table is needed; the picker aggregates distinct values.

**FR-11.7:** Renaming a category updates all notes carrying that category value (app-level batch update in one transaction).

### Structured Templates

**FR-11.8:** Template field definitions come from the seeded `note_templates` lookup (see Data Tables). Field schema per template:

| Template | Fields |
|----------|--------|
| password_login | website, url, username, password, two_fa, notes |
| ott_plan | service, plan_name, cost, billing_date, login, password, shared_with, screens, expiry_date |
| bank_account | bank, account_number, ifsc, branch, account_type, mobile, net_banking_id, customer_id, debit_card, card_expiry |
| card_details | name, card_number, expiry, cvv, billing_date, limit, network, linked_account, rewards |
| insurance_policy | name, provider, policy_number, type, premium, frequency, next_date, sum_assured, maturity, nominee, agent |
| document_id | name, document_number, issue_date, expiry_date, issuing_authority |
| wifi_network | ssid, password, router_url, admin_username, admin_password, isp, speed, cost |

**FR-11.9:** Fields marked `sensitive` in the template schema (password, CVV, card_number, account_number, etc.) are: masked with a reveal toggle in the UI, encrypted client-side with the rest of the payload, and never auto-filled into any search index.

### Freeform Notes

**FR-11.10:** Freeform notes support plain rich text (bold, lists, links). The content is encrypted client-side as a single text blob.

### Search

**FR-11.11:** The search box performs a case-insensitive substring match on `title` server-side (GIN trigram index). Content search runs client-side over the already-loaded, decrypted notes (the browser must decrypt to display anyway). A live result count is shown. At < 500 notes per user, both paths are instant.

### Clipboard Copy

**FR-11.12:** Each field has a copy button. Clicking copies the (decrypted) value to the clipboard and shows a "Copied — clears in 30s" toast. After 30 seconds the clipboard is programmatically cleared (`navigator.clipboard.writeText('')`) — see Security requirement "Clipboard auto-clear (30 seconds) for copied sensitive data".

### Encryption at Rest

**FR-11.13:** Encryption design:
- **Client side (vault):** a per-user vault key is derived (e.g., PBKDF2/AES-GCM from the user's password or a per-user random key wrapped by the user's password) entirely in the browser. Every note payload is serialized to JSON, encrypted with AES-256-GCM, and stored as base64 in `data_encrypted` with the IV/KDF params in `data_iv`. **Plaintext sensitive values never leave the browser.**
- **Server side:** the database resides in encrypted-at-rest storage (Supabase/AWS); additionally, `note_attachments` files are stored encrypted (see F16).
- The `title` is stored in plaintext — it is required for list rendering and server-side search. Users are advised (UI hint) to keep titles non-sensitive.

**FR-11.14:** **Password reset does not affect vault data.** The vault key is a per-user random key (generated at signup, never leaves the browser as plaintext), wrapped by the password-derived key. A recovery copy is kept wrapped under a server-held recovery key (see FR-11.17). On password reset, the user's new password is used to re-wrap the vault key via the recovery path — the vault (and all notes) remain accessible exactly as before. No data loss, no "unrecoverable vault" state.

**FR-11.17 (Vault key lifecycle, cross-ref Module 0 FR-A.18):**
- **Generation:** at signup, the browser generates a random 256-bit vault key + a random recovery key. The vault key is wrapped with the PBKDF2-derived wrap key (from the login password) and stored; the recovery key is wrapped under the server's data-encryption key and stored in `user_settings.vault_recovery_wrapped`.
- **Derivation on login:** the wrap key is derived client-side (PBKDF2 from the password, stored KDF params); the wrapped vault key is unwrapped in the browser only.
- **Destruction on logout:** the in-memory vault key and wrap key are zeroed on logout and on session timeout (FR-A.16); a fresh unlock re-derives them.
- **Password reset / change:** the new password derives a new wrap key; the recovery path unwraps the vault key (server-side with the DEK, delivered to the authenticated client) and re-wraps it with the new wrap key. Vault data is untouched.
- **Server visibility:** only ciphertext ever transits the network; the server never holds the vault key, the wrap key, or the recovery key in plaintext.

### File Attachments

**FR-11.15:** User can attach files to a note (policy PDFs, card photos). Files are encrypted before upload (client-side, same vault key) and stored via the object-storage layer; the `note_attachments` row records name, path, type, size.

**FR-11.16:** Attachments can be downloaded (decrypted client-side), previewed for images/PDFs, and removed. Removing an attachment deletes the stored object and the row.

## Data Tables

### Table: secure_notes

The primary table storing all vault notes. **Sensitive content is client-side encrypted** — see `../data-tables-v2.md` § Module 11.

| Column | Type | Constraints | Index | Description |

| is_pinned | INTEGER | NOT NULL DEFAULT 0 | INDEX idx_notes_pinned | Pin/favorite to top |
| version | INTEGER | NOT NULL DEFAULT 1 | | Optimistic lock |
| created_by | INTEGER | FK → users(user_id) | | Audit |
| updated_by | INTEGER | FK → users(user_id) | | Audit |
| deleted_at | TIMESTAMPTZ | | | Soft delete |

| created_at | TIMESTAMPTZ | NOT NULL DEFAULT CURRENT_TIMESTAMP | | Created timestamp |
| updated_at | TIMESTAMPTZ | NOT NULL DEFAULT CURRENT_TIMESTAMP | | App-managed timestamp |

**Indexes:**
```sql
CREATE INDEX idx_notes_user ON secure_notes(user_id) WHERE deleted_at IS NULL;
CREATE INDEX idx_notes_category ON secure_notes(user_id, category) WHERE deleted_at IS NULL;
CREATE INDEX idx_notes_pinned ON secure_notes(user_id, is_pinned) WHERE deleted_at IS NULL;
CREATE INDEX idx_notes_title_trgm ON secure_notes USING GIN (title gin_trgm_ops);
```

**Performance Notes:**
- Typical usage: 50–500 notes per user lifetime. All queries < 1ms.
- GIN trigram on `title` powers server-side title search (FR-11.11).

## Suggested Enhancements

1. **Auto-lock vault** — Lock the vault after N minutes of inactivity or on tab blur; require password re-entry to decrypt. Complements the app-level session timeout.
2. **Password generator** — Built-in strong password generator inside the Password/Login template with length + character-class options.
3. **Password health check** — Scan Password/Login notes for reused or weak passwords and flag them (client-side analysis only — never send decrypted data anywhere).
4. **Note export/import** — Encrypted vault export (portable file) and restore, so users can back up the vault independently of the DB.
5. **Expiry reminders** — Document/card notes with an expiry date can generate a Notifications Center reminder 30 days before expiry (cross-ref Component C2 trigger table).
6. **Secure share** — Share a single note (or field) with another user via an encrypted, expiring link. Sensitive fields stay encrypted end-to-end.
