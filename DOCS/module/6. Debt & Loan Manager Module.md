# 6. Debt & Loan Manager Module

**Module Type:** Debt Tracking & Payoff Optimization  
**Build Phase:** Phase 2  
**Dependencies:** Module 1 (Account & Wallet), Module 2 (Transaction Engine)

---

## Purpose

Comprehensive debt tracking that helps users understand, manage, and strategically eliminate debt. Supports all common Indian loan types (home, car, personal, education, credit card) with amortization views, prepayment simulation, and payoff comparison strategies.

## Functional Requirements

### Debt Creation & Management

**FR-6.1:** User can add a debt with:
- Name (required, e.g., "Home Loan - SBI", "HDFC Credit Card")
- Type (required, enum: home_loan / car_loan / personal_loan / education_loan / credit_card / other)
- Original Principal (required, positive decimal)
- Outstanding Principal (required, positive decimal, ≤ original principal)
- Interest Rate (required, positive decimal, annual percentage e.g., 8.5 for 8.5%)
- EMI Amount (required for monthly repayment loans, positive decimal)
- Total Tenure (required, in months)
- Months Remaining (required, calculated or user-provided)
- Start Date (required)
- EMI Account (optional, linked account for EMI debits)
- Lender (optional, e.g., "SBI", "HDFC Bank")
- Notes (optional)

**FR-6.2:** For credit card debt, only Outstanding Principal, Interest Rate (annualized), and Minimum Due are required fields. EMI Amount and Tenure are marked as "Revolving" since credit card debt doesn't have a fixed EMI structure.

**FR-6.3:** User can edit debt details. Changes to outstanding principal, interest rate, or tenure recalculate the amortization schedule.

**FR-6.4:** User can mark a debt as "Closed" when fully paid. Closed debts are archived with a "Paid off on [date]" label. They retain full history and amortization schedule.

**FR-6.5:** User can delete a debt only if no EMI payments have been recorded. Otherwise, deactivation is enforced.

### Debt Dashboard

**FR-6.6:** The debt dashboard shows:
- Total outstanding principal across all active debts
- Total monthly EMI burden
- Projected debt-free date (based on current EMI payments without prepayments)
- Total interest that will be paid if loans run to term
- Debt-to-Income ratio (requires user to input monthly income)
- Number of active debts
- A summary card for each debt: name, type, outstanding principal, interest rate, EMI, months remaining, progress bar (months elapsed / total tenure)

**FR-6.7:** Debts are sorted by interest rate descending (highest cost first), then by months remaining ascending.

### Amortization Schedule

**FR-6.8:** For each loan, user can view the full amortization schedule showing per-period (monthly):
- Period number
- EMI amount
- Principal component
- Interest component
- Outstanding principal after payment
- Cumulative interest paid to date

**FR-6.9:** The amortization schedule is client-calculated using the standard formula:
- Monthly Rate = Annual Rate / 12 / 100
- EMI = P × r × (1 + r)^n / ((1 + r)^n - 1) — verified against stored EMI amount

**FR-6.10:** User can filter the amortization schedule by year. A summary for each year shows: total EMI, total principal paid, total interest paid.

**FR-6.11:** A pie chart shows the total cost of the loan split by: total principal vs total interest (over full tenure).

### Prepayment Simulator

**FR-6.12:** User can enter a prepayment amount and select a strategy:
- Reduce EMI (keep tenure same)
- Reduce tenure (keep EMI same)

**FR-6.13:** The simulator outputs:
- New tenure (in months) if reducing tenure
- New EMI amount if reducing EMI
- Total interest saved compared to the original schedule
- New debt-free date
- Side-by-side comparison view: original schedule vs with prepayment

**FR-6.14:** User can apply the prepayment to record an actual prepayment, which updates the outstanding principal and regenerates the amortization schedule.

### Payoff Strategy Comparison (Phase 4 AI-Free Version)

**FR-6.15:** The system provides a manual comparison view where the user can select two strategies:
- **Avalanche** — pay off highest interest rate debt first
- **Snowball** — pay off smallest balance first

**FR-6.16:** User enters an extra monthly amount they can afford. The system calculates for each strategy: total months to debt-free, total interest paid, and total interest saved vs minimum payments.

### EMI Payment Logging

**FR-6.17:** User can log an EMI payment with:
- Amount (defaults to the scheduled EMI)
- Date
- Linked Transaction (optional, can create a new expense transaction)
- Notes

**FR-6.18:** Logged EMI payments automatically reduce the outstanding principal and update months_remaining. A new amortization view is generated reflecting the updated state.

**FR-6.19:** Payment history for each debt shows: date, EMI amount, principal component, interest component, outstanding after payment, linked transaction, notes.

### Debt-to-Income Ratio

**FR-6.20:** DTI is calculated as: (total monthly EMI payments / monthly income) × 100.

**FR-6.21:** The DTI is displayed with a color-coded indicator:
- Green: < 30% (healthy)
- Yellow: 30-40% (moderate)
- Orange: 40-50% (elevated)
- Red: > 50% (concerning)

### Export

**FR-6.22:** Export debt summary as CSV: Name, Type, Outstanding, Interest Rate, EMI, Tenure, Months Remaining, Total Interest to Date.

**FR-6.23:** Export amortization schedule as CSV for any debt: all rows (Period, EMI, Principal, Interest, Balance, Cumulative Interest).

**FR-6.24:** Export prepayment comparison as PDF/PNG.

### Debt List Filters

**FR-6.25:** The debt dashboard has a type filter (multi-select): home_loan / car_loan / personal_loan / education_loan / credit_card / other. Filtering is applied client-side on the loaded list.

**FR-6.26:** User can toggle the dashboard between Active and Closed (archived) debts. Closed debts retain full history and show a "Paid off on [date]" label (FR-6.4). No search box is needed at 1–5 active debts per user.

### EMI Paid/Missed Tracking

**FR-6.27:** Each debt shows a per-month payment timeline (last 12 months). For each scheduled period (from `amortization_schedule`), the status is derived by comparing logged `debt_payments` against the schedule:
- **Paid** — a payment exists for that period
- **Missed** — period passed with no payment (red badge)
- **Scheduled** — period not yet due
The status is always computed on read — no new columns or tables. It drives the "missed payments" flag for debt health alerts (F8) and the Notifications Center (Component C2 trigger 12/6 pattern).

**FR-6.28:** Partial payments (amount < scheduled EMI) count as missed with a "partially paid" tooltip showing the amount logged.

### Combined Multi-Debt Timeline

**FR-6.29:** A consolidated view charts all active debts on a single timeline: each debt as a horizontal bar showing months-to-payoff, stacked by end date. A "Combined Debt-Free Date" is computed as the max of all debts' projected payoff dates. Totals shown: combined outstanding, combined monthly EMI, combined interest to pay if run to term.

**FR-6.30:** The combined view offers the FR-6.15 payoff strategy comparison at portfolio level: entering an extra monthly amount shows the new combined debt-free date and total interest under avalanche vs snowball allocations across all debts.

## Data Tables

### Table: debts

The primary table storing all debt/loan information.

|--------|------|-------------|-------|-------------|
| id | UUID | PK, DEFAULT gen_random_uuid() | PRIMARY KEY | UUID |
| user_id | INTEGER | NOT NULL, FK → users(user_id) ON DELETE CASCADE | | Multi-user owner (covered by composite `idx_debt_active_rate`) |
| name | TEXT | NOT NULL | | Loan name |
| type | TEXT | NOT NULL, CHECK(type IN ('home_loan','car_loan','personal_loan','education_loan','credit_card','other')) | | Loan type |
| lender | TEXT | | | Lender name (e.g., "SBI") |
| principal_original | NUMERIC(12,2) | NOT NULL, CHECK(principal_original > 0) | | Original loan amount |
| principal_outstanding | NUMERIC(12,2) | NOT NULL, CHECK(principal_outstanding >= 0) | | Current outstanding principal |
| interest_rate | NUMERIC(5,2) | NOT NULL, CHECK(interest_rate >= 0) | | Annual interest rate in % |
| emi_amount | NUMERIC(12,2) | NOT NULL, CHECK(emi_amount > 0) | | Monthly EMI amount |
| minimum_due | NUMERIC(12,2) | | | Minimum due (for credit card debt) |
| tenure_months | INTEGER | NOT NULL, CHECK(tenure_months > 0) | | Total loan tenure in months |
| months_remaining | INTEGER | NOT NULL, CHECK(months_remaining >= 0) | | Remaining months |
| start_date | DATE | NOT NULL | | Loan start date |
| end_date | DATE | | | Expected loan end date |
| account_id | UUID | FK → accounts(id) | INDEX idx_debt_account | EMI debit account |
| total_interest_paid | NUMERIC(12,2) | NOT NULL DEFAULT 0 | | Total interest paid to date |
| is_active | INTEGER | NOT NULL DEFAULT 1 | | Active flag (covered by composite) |
| notes | TEXT | | | Optional user notes |
| closed_date | DATE | | | Date debt was closed |
| version | INTEGER | NOT NULL DEFAULT 1 | | Optimistic lock |
| created_by | INTEGER | FK → users(user_id) | | Audit |
| updated_by | INTEGER | FK → users(user_id) | | Audit |
| deleted_at / deleted_by | TIMESTAMPTZ / INTEGER | FK → users(user_id) | | Soft delete |
| created_at | TIMESTAMPTZ | NOT NULL DEFAULT CURRENT_TIMESTAMP | | Created timestamp |
| updated_at | TIMESTAMPTZ | NOT NULL DEFAULT CURRENT_TIMESTAMP | | App-managed timestamp |

> `status` was **removed** — it duplicated `is_active` (drift risk). A debt is **closed** when `is_active = 0` **and** `closed_date` is set (FR-6.4); everything else follows from `is_active`. The Active/Closed dashboard toggle (FR-6.26) filters on `is_active`.

**Composite Indexes:**
```sql
-- Dashboard query: user's active debts sorted by interest rate (highest first)
CREATE INDEX idx_debt_active_rate ON debts(user_id, is_active, interest_rate DESC);
```

**Performance Notes:**
- Typical usage: 1-5 active debts at a time
- Amortization schedule is calculated client-side or cached in `amortization_schedule` — no query overhead for the dashboard
- Even with 20 years of closed debts, total rows rarely exceed 30-50 per user

### Table: amortization_schedule

Optional case for the amortization schedule to avoid recalculating on every view. (Canonical name: `amortization_schedule`, was `amortization_cache`.)

| Column | Type | Constraints | Index | Description |
|---------|------|-------------|-------|-------------|
| id | UUID | PK, DEFAULT gen_random_uuid() | PRIMARY KEY | UUID |
| user_id | INTEGER | NOT NULL, FK → users(user_id) ON DELETE CASCADE | | Multi-user owner (covered by composite `idx_ac_debt_period`) |
| debt_id | UUID | NOT NULL, FK → debts(id) ON DELETE CASCADE | INDEX idx_ac_debt | Parent debt |
| period | INTEGER | NOT NULL | | = 1 based |
| emi_amount | NUMERIC(12,2) | NOT NULL | | EMI for this period |
| principal_part | NUMERIC(12,2) | NOT NULL | | Principal component |
| interest_part | NUMERIC(12,2) | NOT NULL | | Interest component |
| outstanding_after | NUMERIC(12,2) | NOT NULL | | Outstanding principal after payment |
| cumulative_interest | NUMERIC(12,2) | NOT NULL | | Total interest paid to this point |
| scheduled_date | DATE | | | Scheduled date for this period |
| regenerated_at | TIMESTAMPTZ | | | When this cache was last rebuilt (stale-detection) |

**Composite Index:**
```sql
CREATE INDEX idx_ac_debt_period ON amortization_schedule(user_id, debt_id, period);
```

**Note:** This table is regenerated whenever the debt's principal, interest rate, or tenure changes (including after an EMI payment or prepayment). `regenerated_at` is updated in the same write transaction so the app can detect a stale cache. The amortization itself is computed client-side and optionally cached here for quick re-rendering.

## Database Indexing Strategy

### Index Creation SQL

```sql
-- Debts table (multi-user aware)
CREATE INDEX idx_debt_account ON debts(account_id);
CREATE INDEX idx_debt_active_rate ON debts(user_id, is_active, interest_rate DESC);

-- Debt Payments
CREATE INDEX idx_debt_transaction ON debt_payments(transaction_id);
CREATE INDEX idx_dp_debt_date ON debt_payments(user_id, debt_id, date DESC);

-- Amortization Schedule
CREATE INDEX idx_ac_debt ON amortization_schedule(debt_id);
CREATE INDEX idx_ac_debt_period ON amortization_schedule(user_id, debt_id, period);
```

### Query Performance Benchmarks (Target)

| Query | Target Time | Index Used |
|-------|-------------|------------|
| Get all active debts sorted by interest rate (user) | < 0.5ms | idx_debt_active_rate |
| Get debt by ID (scoped to user) | < 0.5ms | PRIMARY KEY (user scoping via RLS) |
| Get payment history for a debt (user) | < 1ms | idx_dp_debt_date |
| Calculate total outstanding across all debts (user) | < 0.5ms | idx_debt_active_rate (aggregate on active) |
| Log EMI payment (insert + update debt) | < 2ms | PRIMARY KEY + idx_dp_debt_date |
| Get amortization schedule (from cache) | < 1ms | idx_ac_debt_period |
| Recalculate amortization schedule | < 10ms | client-side calculation + batch insert |
| Get debt-to-income ratio (total EMI) | < 0.5ms | idx_debt_active_rate (sum of emi_amount) |
| Export debt summary | < 3ms | idx_debt_active_rate |

## Suggested Enhancements

1. **Interest rate change logging** — Loans with floating interest rates change over time. Instead of editing the single `interest_rate` field, maintain a `debt_rate_history` table with effective dates and rates. The amortization schedule uses the correct rate for each period. Essential for home loans with floating rates (very common in India).

2. **EMI holiday tracking** — Some loans allow a moratorium period or users may request a payment holiday. Support `debt_holidays` with start/end dates. During a holiday, no EMI is due but interest may continue accruing.

3. **Balance transfer / refinancing** — Allow users to record a debt balance transfer (moving a loan from one bank to another at a lower rate). The old debt is closed, a new debt is created with the reduced rate, and the system shows the interest savings from the transfer.

4. **Credit card revolving tracking** — Credit card debt behaves differently from term loans. Instead of a fixed EMI, track: current balance, minimum due, interest-free period, and payment due date. The system could track the "cost of revolving" — how much interest is incurred by paying only the minimum due.

5. **Debt consolidation view** — When a user has multiple debts, provide a consolidated view showing: total outstanding, total EMI, and a "Debt Snowfall" chart showing how each debt gets eliminated over time with minimum payments vs accelerated payments.

6. **Goal-linked debt payoff** — If a user pays off a debt, the freed-up EMI amount can be redirected to a savings goal. The system suggests: "Your Car Loan EMI of ₹12,000 ends in 3 months. Redirect this to your Emergency Fund goal?" This bridges Module 6 (Debt) and Module 5 (Goals).
